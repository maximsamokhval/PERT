# Feature Specification: PERT Estimation SDLC Tool

**Feature Branch**: `001-pert-estimation-sdlc`
**Created**: 2026-04-02
**Status**: Draft
**Input**: User description: "як керівник розробки я хочу отримати інструмент для PERT Estimation SDLC. я как архитектор створюю нову сесію оцінювання, додає робочі елементи, вводить значення O/M/P (Оптимістичне/Найбільш імовірне/Песимістичне) і бачить метрики PERT, що оновлюються в реальному часі. Сесія зберігається автоматично. Дано: сесія в статусі 'Чернетка' → Коли: введено валідні O/M/P → Тоді: $t(E)$, розмах (spread), $\sigma$, дисперсія, прихований резерв, загальні трудовитрати та тривалість перераховуються миттєво без перезавантаження сторінки. Архітектор переглядає оцінки, візуально ідентифікує елементи з високим розмахом і переглядає значення. Сесії залишаються доступними для редагування до моменту явного схвалення. Архітектор схвалює сесію та експортує елементи як задачі (issues) у систему трекінгу задач. Система записує отримані ID задач назад у кожен елемент оцінювання. Архітектор генерує PDF або ділиться публічним посиланням лише для читання. Клієнт бачить оцінку без створення акаунта. Архітектор один раз налаштовує системне підключення до YouTrack і визначає мапінг полів для кожного проєкту, який використовується повторно."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Створення та редагування сесії оцінювання (Priority: P1)

Архітектор створює нову сесію оцінювання, додає робочі елементи (наприклад, задачі, епіки), вводить для кожного елемента три оцінки часу: оптимістичну (O), найбільш імовірну (M), песимістичну (P). Система миттєво розраховує та відображає метрики PERT: очікуваний час t(E), розмах (spread), стандартне відхилення σ, дисперсію, прихований резерв, загальні трудовитрати та тривалість. Сесія автоматично зберігається зі статусом "Чернетка". Архітектор може редагувати будь-який елемент, і метрики перераховуються в реальному часі без перезавантаження сторінки.

**Why this priority**: Це основна функціональність інструменту, без якої неможливо використовувати PERT оцінку. Забезпечує миттєвий зворотний зв'язок та точність розрахунків.

**Independent Test**: Можна повністю протестувати, створивши сесію, додавши один елемент з O/M/P значеннями та перевіривши, що метрики розраховуються правильно і відображаються без перезавантаження.

**Acceptance Scenarios**:

1. **Given** порожня сесія в статусі "Чернетка" (FF=0.8, hours_per_day=8, k=0.1), **When** архітектор додає новий робочий елемент з валідними значеннями O=2, M=4, P=8 (години), **Then** система розраховує t(E)=4.33, spread=6, σ=1, дисперсію=1, прихований резерв=0.60 (Δ=6, k=0.1), загальні трудовитрати=4.93, тривалість=0.77 дні та відображає їх миттєво.
2. **Given** сесія з одним елементом (O=2, P=8), **When** архітектор змінює значення M з 4 на 6, **Then** метрики перераховуються миттєво (t(E)=5.67, spread=6, σ=1, R=0.60, TE=6.27, D=0.98 дні тощо) без перезавантаження сторінки.
3. **Given** сесія з кількома елементами, **When** архітектор видаляє один елемент, **Then** загальні трудовитрати та тривалість перераховуються з урахуванням решти елементів.

### User Story 2 - Візуальна ідентифікація елементів з високим розмахом та аналіз (Priority: P2)

Архітектор переглядає список елементів сесії. Система візуально виділяє (наприклад, кольором або іконкою) елементи з високим розмахом (spread > порогового значення). Архітектор може швидко ідентифікувати такі елементи, переглянути їх значення O/M/P та прийняти рішення про уточнення оцінок.

**Why this priority**: Допомагає архітектору зосередитися на найбільш невизначених елементах, покращуючи точність оцінки. Критично для якості планування.

**Independent Test**: Можна протестувати, створивши два елементи: один з малим розмахом (O=3,M=4,P=5), інший з великим (O=1,M=4,P=10). Перевірити, що система правильно виділяє другий елемент.

**Acceptance Scenarios**:

1. **Given** сесія з елементами, що мають різний розмах, **When** архітектор відкриває список елементів, **Then** елементи з розмахом > spread_threshold (default: 5 годин, налаштовується в Session.spread_threshold) візуально виділені.
2. **Given** виділений елемент з високим розмахом, **When** архітектор натискає на нього, **Then** відкривається детальний перегляд з можливістю редагування O/M/P.

### User Story 3 - Схвалення сесії та експорт задач у YouTrack (Priority: P3)

Архітектор, завершивши оцінку, схвалює сесію (змінює статус з "Чернетка" на "Схвалено"). Після схвалення система експортує кожен робочий елемент як задачу (issue) у YouTrack згідно з налаштованим мапінгом полів проекту. YouTrack повертає ID створених задач, система записує ці ID у відповідні елементи оцінювання для подальшого відстеження.

**Why this priority**: Забезпечує інтеграцію з системою трекінгу задач, автоматизуючи процес створення задач на основі оцінки. Зменшує ручну роботу та помилки.

**Independent Test**: Можна протестувати, налаштувавши тестове підключення до YouTrack, створивши сесію з одним елементом та схваливши її. Перевірити, що задача створена в YouTrack, а ID записано в елемент.

**Acceptance Scenarios**:

1. **Given** сесія в статусі "Чернетка" з двома елементами, **When** архітектор натискає "Схвалити", **Then** статус сесії змінюється на "Схвалено", редагування елементів блокується.
2. **Given** схвалена сесія, **When** система експортує елементи до YouTrack, **Then** для кожного елемента створюється задача з полями (назва, опис, оціночний час) згідно мапінгу проекту.
3. **Given** експорт завершено, **When** YouTrack повертає ID задач, **Then** система зберігає ці ID у відповідних елементах оцінювання та відображає їх у інтерфейсі.

### User Story 4 - Генерація PDF та публічне посилання для клієнта (Priority: P4)

Архітектор може згенерувати PDF-звіт із деталями оцінки (елементи, метрики, графіки) або отримати публічне посилання лише для читання. Клієнт (наприклад, замовник) може переглянути оцінку за цим посиланням без необхідності створювати обліковий запис або автентифікуватися.

**Why this priority**: Забезпечує прозорість та комунікацію з клієнтом, дозволяє ділися результатами оцінки без технічних бар'єрів.

**Independent Test**: Можна протестувати, створивши сесію, згенерувавши PDF та перевіривши, що файл містить усі необхідні дані. Також перевірити, що публічне посилання відкриває сторінку лише для читання без можливості редагування.

**Acceptance Scenarios**:

1. **Given** схвалена сесія, **When** архітектор натискає "Згенерувати PDF", **Then** система створює PDF-файл з назвою сесії, датою, таблицею елементів та метриками, який можна завантажити.
2. **Given** схвалена сесія, **When** архітектор натискає "Отримати публічне посилання", **Then** система генерує унікальне посилання, яке відкриває сторінку лише для читання з даними сесії.
3. **Given** публічне посилання, **When** клієнт відкриває його в браузері без автентифікації, **Then** він бачить всі дані оцінки, але не може редагувати або схвалювати.

---

### Edge Cases

- Що робити, якщо значення O/M/P невалідні (наприклад, O > M > P не дотримується)? Система повинна показувати помилку та не розраховувати метрики.
- Як система обробляє втрату зв'язку з YouTrack під час експорту? Система показує помилку користувачеві без автоматичних повторних спроб; архітектор може вручну повторити експорт після усунення проблеми.
- Що робити, якщо клієнт намагається редагувати сесію через публічне посилання? Система повинна показувати повідомлення про те, що доступ лише для читання.
- Як система поводиться, якщо архітектор намагається схвалити сесію з порожніми елементами? Повинна бути перевірка на наявність хоча б одного елемента з валідними O/M/P.
- Що робити, якщо два архітектори одночасно редагують одну сесію? Система повинна використовувати оптимістичне блокування: при спробі зберегти зміни, якщо дані вже оновлені іншим користувачем, показувати попередження про конфлікт та пропонувати вирішити його (наприклад, перезавантажити актуальні дані).
- **Нові edge cases**:
  - Якщо FF (Focus Factor) встановлено в 0, система повинна показувати validation error (ділення на нуль заборонено).
  - При клонуванні схваленої сесії поле `tracker_issue_id` очищується, а `export_status` змінюється на `not_exported`.
  - Якщо архітектор намагається повернути сесію зі статусу "Схвалено" до "Чернетка", система показує явне повідомлення з поясненням, що це заборонено, і пропонує опцію клонування.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST дозволяти архітектору створювати нові сесії оцінювання з назвою, описом та статусом "Чернетка".
- **FR-002**: Система MUST дозволяти архітектору додавати, редагувати та видаляти робочі елементи в сесії.
- **FR-003**: Для кожного робочого елемента система MUST надавати поля для введення трьох числових оцінок: оптимістичної (O), найбільш імовірної (M), песимістичної (P) у годинах.
- **FR-004**: Система MUST автоматично розраховувати та відображати метрики PERT для кожного елемента та всієї сесії в реальному часі при зміні O/M/P: очікуваний час t(E), розмах (spread), стандартне відхилення σ, дисперсію, прихований резерв, загальні трудовитрати, тривалість.
- **FR-005**: Система MUST автоматично зберігати зміни в сесії без явного збереження користувачем.
- **FR-006**: Система MUST візуально виділяти елементи з високим розмахом (spread > порогового значення) для полегшення ідентифікації.
- **FR-007**: Система MUST надавати можливість архітектору схвалити сесію, змінюючи статус з "Чернетка" на "Схвалено", після чого редагування елементів блокується.
- **FR-008**: Система MUST експортувати кожен робочий елемент схваленої сесії як задачу (issue) у YouTrack, використовуючи налаштований мапінг полів проекту.
- **FR-009**: Система MUST записувати отримані з YouTrack ID задач у відповідні елементи оцінювання для подальшого відстеження.
- **FR-010**: Система MUST надавати можливість генерації PDF-звіту з деталями оцінки для завантаження.
- **FR-011**: Система MUST надавати можливість створення публічного посилання лише для читання, за яким клієнт може переглядати оцінку без автентифікації.
- **FR-012**: Система MUST дозволяти архітектору налаштувати системне підключення до YouTrack один раз та визначити мапінг полів для кожного проекту, який використовується повторно.
- **FR-013**: Система MUST забезпечувати валідацію введених O/M/P значень (O ≥ 1, O ≤ M ≤ P, всі цілі числа ≥ 1) та показувати помилки при невалідних даних. Значення нижче 1 заборонені, оскільки формула PERT вимагає додатних значень, а мінімальна одиниця оцінки — 1 година.

### Key Entities *(include if feature involves data)*

- **Сесія оцінювання**: Представляє оцінку проекту, має назву, опис, статус (Чернетка/Схвалено), список робочих елементів, загальні метрики.
- **Робочий елемент**: Представляє задачу або епік, що оцінюється. Має назву, опис, значення O/M/P, розраховані метрики (t(E), spread, σ, дисперсія, прихований резерв), посилання на задачу YouTrack (ID).
- **Мапінг полів проекту**: Визначає, як атрибути робочого елемента (назва, опис, оціночний час) мапуються на поля задачі YouTrack (наприклад, Summary, Description, Custom Field).
- **Публічне посилання**: Унікальний ідентифікатор, що надає доступ лише для читання до сесії оцінювання без автентифікації.
- **ExportMapping**: Додаткові поля для експорту робочого елемента у трекер задач (work_type, subsystem, assignee, analyst, developer, priority, start_date, lead_time). Пов'язаний з конкретним робочим елементом, не є частиною PERT-розрахунків.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Архітектор може створити нову сесію оцінювання та додати перший робочий елемент з O/M/P значеннями менш ніж за 2 хвилини.
- **SC-002**: Зміна значень O/M/P будь-якого елемента призводить до оновлення метрик PERT на екрані протягом менш ніж 1 секунди.
- **SC-003**: Після схвалення сесії всі робочі елементи експортуються як задачі в YouTrack з успішним створенням задач для 95% елементів.
- **SC-004**: Клієнт може відкрити публічне посилання та переглянути повну оцінку без автентифікації за менш ніж 5 секунд.
- **SC-005**: Архітектор може ідентифікувати елементи з високим розмахом (spread > 5 годин) за візуальними індикаторами протягом 10 секунд після відкриття сесії.

## Assumptions

- Архітектор має обліковий запис у YouTrack з правами на створення задач у відповідних проектах.
- Клієнт має доступ до інтернету та сучасний веб-браузер для перегляду публічного посилання.
- Усі розрахунки PERT виконуються на стороні клієнта або сервера з достатньою продуктивністю для миттєвого оновлення.
- Система зберігає дані сесії в постійному сховищі (SQLite з WAL mode). Автоматичне резервування бази даних — поза межами MVP (out of scope).
- Інтеграція з YouTrack використовує API YouTrack з підтримкою токенів доступу.
- Порогове значення для високого розмаху може бути налаштоване (за замовчуванням 5 годин).
- Сесія оцінювання обмежена максимум 100 робочими елементами для забезпечення продуктивності.
- Архітектор повинен мати обліковий запис у системі інструменту (окрема автентифікація) для доступу до сесій оцінювання.

## Clarifications

### Session 2026-04-02

- Q: Як система повинна обробляти одночасне редагування однієї сесії оцінювання кількома архітекторами? → A: Оптимістичне блокування з попередженням про конфлікт при збереженні.
- Q: Яке обмеження на кількість робочих елементів у сесії оцінювання? → A: Максимум 100 робочих елементів на сесію.
- Q: Який метод автентифікації архітектора використовувати? → A: Окрема автентифікація в інструменті (логін/пароль або OAuth окремий).
- Q: Чи потрібен журнал змін (audit log) для сесії оцінювання? → A: Журнал змін не ведеться (лише поточний стан).
- Q: Яка стратегія повторних спроб при збоях API YouTrack під час експорту? → A: Одразу показувати помилку користувачеві без повторних спроб.

### Session 2026-04-02 (API Contract Fixes)

- Q: Як опрацювати MappableItemField неповноту? → A: Створити окрему модель `ExportMapping` для додаткових полів експорту.
- Q: Як опрацювати відсутність AUTHENTICATION_ERROR в ErrorCode? → A: Додати `AUTHENTICATION_ERROR = "authentication_error"` до ErrorCode StrEnum.
- Q: Як конвертувати total_effort (float години) в YouTrack period формат? → A: Utility функція `hours_to_period(hours: float) -> str`: `hours=8.8 → "8h 48m"`.
- Q: Як виправити невалідний focus_factor: 0.75 в PATCH прикладі? → A: Замінити `0.75` → `0.8` (найближче валідне значення).

## Canonical PERT Formula Reference

All item-level metrics are stored and returned in **hours**.
Session-level duration is converted to **days** using session parameters.
**All calculated metrics MUST use 3 decimal precision** (e.g., 4.333, 0.772).

| Symbol | Name | Formula | Unit |
|--------|------|---------|------|
| O | Optimistic | Input | h |
| M | Most Likely | Input | h |
| P | Pessimistic | Input | h |
| t(E) | Expected time | `(O + 4M + P) / 6` | h |
| Δ | Spread | `P − O` | h |
| σ | Std deviation (item) | `Δ / 6` | h |
| V | Variance (item) | `σ²` | h² |
| R | Hidden Reserve | `Δ × k` | h |
| TE | Total Effort (item) | `t(E) + R` | h |
| σ_tot | Std deviation (session) | `√(ΣV)` | h |
| B₉₅ | 95% Contingency Buffer | `1.645 × σ_tot` | h |
| Σ TE | Total Effort (session) | `Σ TE` (**B₉₅ excluded**) | h |
| D_item | Duration (item) | `TE / (FF × hours_per_day)` | days |
| D_session | Duration (session) | `Σ TE / (FF × hours_per_day)` | days |

**Why B₉₅ is always separate from Σ TE:**
The buffer is a risk reserve, not a committed cost. Mixing them into a single
number hides the uncertainty component from the decision-maker. The UI MUST
display both independently.

**Why `R = Δ × k` and not `t(E) × k`:**
Hidden reserve compensates for work uncertainty, not for expected duration.
Uncertainty is captured by spread (Δ). Using t(E) as the base would
double-count the expected value. `k` is calibrated against Δ.

**Why `D = TE / (FF × hours_per_day)` and not just `TE / hours_per_day`:**
Focus Factor (FF) models the reality that engineers are not 100% productive
during working hours (meetings, context switching, support). Without FF,
duration estimates are systematically optimistic.

Parameters: O=2, M=4, P=8, k=0.1, FF=0.8, hours_per_day=8
